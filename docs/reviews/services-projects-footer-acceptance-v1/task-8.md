Rulings
1. **Helper not used.** The plan's D4 exception lets the lead do the mechanical part inline when no suitable helper can be spawned. Luna (`gpt-6-luna`) cannot be spawned from this runtime, and a Sonnet 5.5 worker is the lead's own model, so it would add a handoff, a worktree and a second context with no cost advantage (the D4 cost argument is that the helper is cheaper). The capture, encoding and derivatives are deterministic scripts. Cost if wrong: none to correctness; the owner's permission to delegate was not exercised.
2. **One composition for both routes.** The scene and its graph are shared by Services and Projects, so the two posters are the same composition at the same pose (they differ only in sub-pixel idle angle, hence the 116256 against 116052 bytes). The manifest keeps four files by route and quality because Task 2 defined it that way. Cost if wrong: re-capture one route at another pose; the owner may want visibly different variants.
3. **Pose.** Progress 0.60 and idle angle 0.50 rad: at 0.40 the network reads half-built with isolated tracer dots, at 0.80 it is dense behind the hero; 0.60 is the first state where most connections are grown and every node is in frame. Cost if wrong: re-run the script with another constant.
4. **Pinned ratio.** `aspect-ratio: 1599 / 900` on the dossier image. Without it a loaded derivative replaces the reserved box by the image's own ratio (640×360 is 1.7778, the original 1.7767), which moved the text below each image by about one pixel in the Projects baselines and is a small layout shift. Cost if wrong: remove the declaration and accept the shift.
5. **Plain `<img>` with `srcSet`.** The bundled Next.js documentation says `next/image` does not forward `srcSet`, and the static export is `unoptimized`, so the responsive candidates had to be listed by the page. The packet's "picture selection" is met with `srcset` and `sizes` on one `<img>`; the Ground keeps its Task 2 CSS selection (a background image the browser fetches once, at the 768px boundary), which satisfies "selects the wide or compact poster at the 768px boundary" without a second mechanism. Cost if wrong: wrap in `<picture>`.
6. **Out-of-set test edits, made so the suite is green, pending the owner.** `scripts/projects-publication.test.mjs` pinned `public/projects` to exactly the two originals and `scripts/project-details.test.mjs` asserted the `next/image` import; both are Task 3 files and neither is in the Task 8 write set. Each edit is one narrow assertion, dated in a comment. Cost if the owner declines: revert them and rework the wiring; the suite is red until then.

Findings
1. The posters: all four are within their ceilings (116 KiB and 50 KiB at most), at their intrinsic sizes, opaque, with no label text and no development overlay. The CSS chart stays the final fallback (the 404 case).
2. `next dev` lists the engine chunk in every connected page, so "no engine request" cannot be asserted by request under dev; the development counter (`imports === 0`, `mode` static) is used, as in Task 7's specs.
3. **Static-to-live continuity is not exact (for the owner and Task 9).** The poster is the scene at progress 0.60 and idle angle 0.50 rad, while a live session starts at the top of the page, progress 0, angle near 0. Nodes sit within a few tens of pixels of each other and the grown paths differ (compare the exploration frames at progress 0 and 0.62), so a fade from poster to live would show the network "retracting". Both live tiers are off in every merged build, so no visitor sees it today. Options for the owner: accept the crossfade, or capture at progress 0 (a weaker still), or add a start pose to the host (Task 7's file, not this PR's).
4. `loading="lazy"` images are fetched by the browser's own distance threshold: Chromium fetched the second dossier image 2335px below the fold on load. The assertion is the attribute, not the moment.
